# AskRex Development Orchestrator

## Purpose

The development orchestrator keeps the backend/desktop and mobile AskRex workstreams moving without requiring repeated browser-chat continuation prompts. It is an operator/development tool, not part of the shipped AskRex runtime.

The orchestrator combines:

- deterministic Python supervision and durable state;
- Claude Code implementation loops with Codex as the implementation fallback;
- optional Claude Code cloud implementation sessions on isolated pushed GitHub branches;
- ChatGPT-subscription Codex planning/review first, with metered OpenAI API reasoning only as fallback;
- emergency-only GPT-6 Astra adjudication after the Sol chain remains explicitly unresolved;
- the shared cross-instance coordination protocol;
- a model-free Windows watchdog.

The authoritative design is `docs/superpowers/specs/2026-09-10-development-orchestrator-design.md`.

## Repository ownership

Backend/desktop and mobile remain separate workstreams. The supervisor may route work and read shared coordination state, but it does not grant one worker permission to edit the other repository.

Never configure `C:\Users\james\rex-ai-test\rex-ai-pc-test` as a development worker. That worktree remains frozen for live acceptance testing.

## Model routing

Every invocation selects its provider/model explicitly. Do not rely on the user's global Codex default. OpenAI API routing is disabled by default.

| Phase | Primary | Fallback |
|---|---|---|
| Implementation | Claude Cloud when mode=`preferred`, otherwise local Claude `sonnet` / escalated `opus` | Claude Cloud when mode=`fallback`, then Codex implementation |
| Routine review | Codex `gpt-5.6-terra` via ChatGPT subscription | OpenAI API `gpt-5.6-terra` |
| Escalated review | Codex `gpt-5.6-sol` via ChatGPT subscription | OpenAI API `gpt-5.6-sol` |
| Review after Codex implementation | Codex `gpt-5.6-sol` via ChatGPT subscription | OpenAI API `gpt-5.6-sol` |
| Planning | Codex `gpt-5.6-sol` via ChatGPT subscription | OpenAI API `gpt-5.6-sol` |
| Adjudication | Codex Sol via ChatGPT subscription, then API Sol fallback | API `gpt-6-astra` only after a valid unresolved `failed` result and all emergency gates |
| `FINAL-VERIFY-*` | Codex `gpt-5.6-sol` only | none |

Astra is not a routine planner, reviewer, implementer, or final verifier. It may be attempted at most once for a revision-bound task escalation episode. API/Codex transport unavailability alone never justifies Astra; the lower-cost Sol chain must produce a valid explicitly unresolved result first.

## Ralph-style lifecycle

Each repo has one durable current task and one state: `idle`, `planning`, `implementing`, `reviewing`, `blocked_user`, `blocked_system`, or `done`.

Implementation may return `continue` or `ready_for_review`. A published `ready_for_review` checkpoint must pass the supervisor's configured deterministic local validation gates before the workstream may enter independent review. Explicit coordination-only closeouts use a lightweight default profile (coordination recheck, unchanged checkpoint, and diff check) unless trusted configuration supplies a stronger task-specific override; they do not inherit the full product-code test suite merely because they run on a backend/mobile role. The current matching revision-bound receipt defines the deterministic gates the reviewer may require, so superseded failures and unrelated unconfigured gates are not valid reasons to reopen implementation. Successful validation clears prior implementation/reviewer feedback from the authoritative review input. Two review rejections on a coordination-only task with a current green receipt trigger Astra adjudication instead of another ordinary implementation loop; Astra may close only such no-code coordination work and cannot waive source, security, permission, or authority defects. A fixed-needs-retest issue update hands the remaining physical acceptance to testing and returns the development role to idle/planning rather than blocking that role until the retest occurs. Normal gate failures return the exact gate, command, exit code, and captured output to implementation feedback; validation-infrastructure failures park as `blocked_system` while preserving the durable implementation result so recovery retries validation without reinvoking the worker. Independent review must return `pass` before the task is cleared. Current contents of changed files are included for small diffs so reviewers can verify surrounding pre-existing regression/source context without reconstructing it through a shell. Task-matching canonical live-test issue state is included separately from the generic coordination snapshot so mailbox/context bounding cannot hide the issue status needed for review. Those current-file snapshots are supplemental: if they exceed their evidence budget while the authoritative task diff and matching validation receipt remain complete, truncate the snapshots without invalidating the whole review bundle or falling back to the thin coordination context. Direct Codex review consumes the same revision-bound bounded evidence and is tool-free: it must not invoke terminal/shell/repository/Web/MCP tools; when a material fact is absent it returns changes_required naming that evidence instead. Reviewed completions are persisted in the supervisor completed-task ledger. The planning lead receives that bounded history, and a planner assignment that maps to a reviewed completion is rejected before implementation while the reviewed checkpoint remains an ancestor of the current branch. Stale mailbox Needs-response entries therefore cannot resurrect already-reviewed work; a genuine regression must be represented by new explicit work. After a reviewed task clears to idle, idle is only a transient scheduling state: on the next cycle the supervisor plans the next bounded task even when repository and coordination context are otherwise unchanged. Explicit queued work is checked first and always wins. A role parks only for a truthful blocker, observe-only mode, or a verified done transition through deterministic completion and final-review gates; completing one ordinary task never stops an active campaign. `changes_required` returns review feedback to the implementer. Repeated failures escalate within the configured routing policy. Phase escalation is journal-safe: the supervisor records/applies the triggering result and clears its durable pending receipt before invoking adjudication or any other next model phase. Astra is considered only for adjudication after the API Sol and Codex Sol chain returns a valid explicitly unresolved `failed` result and the emergency threshold/episode/budget gates pass.

A blocker affects only its workstream. Backend may continue while mobile awaits an iPhone test, and mobile may continue while backend awaits a Windows acceptance step. Backend and mobile role cycles execute independently so one long model invocation does not serialize the other workstream.

## Coordination authority

Workers receive a bounded read-only snapshot of protocol, role mailbox, and owned issues. They do not receive filesystem write access to the authoritative coordination root. Mailbox messages and owned issue transitions are returned as structured result fields; the deterministic supervisor validates recipient, ownership, and status before writing them. Development may request `fixed-needs-retest` but never writes the canonical `TEST-*.md` status. The supervisor emits an atomic retest request to `mailbox/testing`; the testing role alone updates canonical live-test status and verification.

Activation requires an exclusive nonce-based lease for both development worktrees. The supervisor creates a request bound to a browser-session correlation identifier. The trusted local Windows operator verifies that the browser worker checkpointed and stopped writing, then records `operator-ack-handoff`. The session identifier is correlation evidence, not cryptographic authentication. Lease acceptance records the operator identity, waits through a quiescence interval, and revalidates the linked non-protected worktree, expected GitHub repository, exact `origin/<current-branch>` upstream, branch, HEAD, and cleanliness. Supervisor and per-role control-plane lock pathnames persist; ownership is an OS/kernel-held exclusive file lock and is never reclaimed by PID inspection or pathname deletion. Claude commits must include the invocation trailer supplied by the supervisor, and every post-invocation commit is verified against that provenance before the lease HEAD advances. Every production model invocation uses a disposable scratch clone instead of the leased live worktree. Claude runs inside the pinned `askrex-claude-code:2.1.238` Docker sandbox as a non-root user with Linux capabilities dropped, `no-new-privileges`, and no Bash tool. Production model prompts are streamed over stdin rather than embedded in Windows process argv, preventing large coordination/review/validation context from exceeding `CreateProcess` command-line limits. Subscription-authenticated Codex is the first implementation provider. Only a classified Codex usage/authentication limit selects the existing isolated Claude CLI subscription fallback. Automatic implementation never creates a new cloud session, regardless of the retained cloud-mode setting. While a cloud task is active Ralph only polls that bound session and never launches a duplicate. A completed cloud branch is adopted only after the exact completion commit and unchanged local dispatch HEAD are verified, then it enters the same deterministic validation and independent Codex review gates. An unresolved existing cloud session is recovered only through its bound polling/adoption path; missing or mismatched ownership fails closed without dispatching another worker. The Codex fallback prompt permits only workspace-local repository/terminal tools inside that scratch clone; it does not inherit Claude's no-shell instruction and still forbids Web/network/MCP access and Git commits. Codex review/lead commands remain read-only with both cwd and `-C` rewritten to their scratch clone; OpenAI API reasoning remains tool-free, read-only, and same-HEAD. On Windows, Codex CLI invocations use the `windows.sandbox="elevated"` backend because the unelevated backend reproducibly suffers intermittent child-process initialization failures (`0xC0000142`); the authority boundary remains the disposable scratch clone plus Codex `workspace-write` for implementation/read-only for review and lead, with out-of-workspace writes denied. Codex terminal startup failures that report `connecting runner pipe-in` timeouts or `Failed to create unified exec process` are treated as transient runtime faults: on Windows the supervisor terminates stale `codex-command-runner.exe` helpers and, when the packaged `CodexSandboxService.OpenAI.Codex` service is installed, restarts that SCM-managed sandbox service and waits for Running before the next bounded retry; standalone `codex-windows-sandbox-service.exe` termination is retained only as a legacy fallback when the managed service restart is unavailable, whether the fault surfaced as a nonzero CLI failure or a structured agent blocker, the affected phase is parked as `blocked_system`, retried automatically with at least four bounded recovery attempts (or a higher configured implementation/review limit), and only remains blocked after that recovery budget is exhausted; these failures must not be surfaced as a `blocked_user` request. A checkpoint implemented by Codex is independently reviewed by a fresh GPT-5.6 Sol review invocation. If both Claude and Codex are usage-limited, the workstream pauses through the existing usage-limit blocker instead of retrying continuously. All agent output must pass the canonical Draft 2020-12 JSON Schema before any state change, coordination write, or repository publication. Successful Codex review/lead and OpenAI reasoning output is schema-validated before lease advancement. Every production Claude result, including blocked or failed outcomes that carry coordination messages, must also echo the exact active role, task ID, and unpredictable invocation ID before any live side effect. For successful implementation outcomes only, the supervisor creates the invocation-provenance commit inside the scratch clone, revalidates the live HEAD/clean state, imports that immutable direct-child commit, and fast-forwards the live worktree while holding the per-role lease lock. Custom executors are test-only, require every configured runtime path to live beneath the system temporary root, receive only scratch clones, must leave their configured repository unchanged, and never publish or advance leased repositories. Custom executors are trusted test fixtures only, require explicit test opt-in and temporary runtime paths, and are not a security boundary for hostile callback code. Repository-state seals and child-process cleanup provide defense-in-depth against accidental ambient mutation, including hidden refs, scratch-origin pushes, modify-then-restore writes, exception paths, and Windows reparse traversal; untrusted or adversarial callbacks must never be supplied through this hook. Coordination mailbox publication is a recoverable transaction: a durable manifest precedes visibility, destinations are confined beneath `mailbox/`, partial writes roll back, abandoned manifests recover under the publication lock, and supervisor startup performs recovery before normal work. Launcher image inspection plus watchdog container inspection/cleanup distinguish present, absent, and unknown Docker state; images are built only when definitively absent, and daemon or inspect ambiguity fails closed. Each production scratch has a random ownership nonce stored in an ownership manifest and activity marker; watchdog deletion verifies nonce, canonical path, role, invocation ID, pre-HEAD, Git top-level/HEAD, and rejects the root or any descendant reparse point, captures a stable Windows filesystem identity immediately before quarantine, atomically renames the verified scratch parent into a private quarantine path, requires the same filesystem identity after rename, revalidates provenance and reparse safety there, and deletes it with a non-reparse-following primitive; ambiguous rename/revalidation/deletion fails closed and retains quarantine.

### Rejected implementation checkpoints

An original task that explicitly prohibits repository edits keeps that restriction through retries. Codex uses its read-only scratch mode and Claude mounts its scratch read-only. The implementation prompt requests inspection and bounded structured coordination output, without worker tests, builds, formatting, dependency installation, shared coordination writes, or a repository checkpoint. The host still runs the configured canonical gates. Before publication, the host independently rejects staged repository changes for such a task, even when their whitespace check passes. Ordinary authorized implementation tasks retain their existing scratch commit and publication behavior.

The host preserves the bound original model result and output before its Git gates. A known scratch whitespace failure or original-task scope rejection becomes a separate `prepublication_gate_failure` checkpoint under `postprocessing-failures/`, with actual command results, immutable output/index/patch hashes, the original task binding, and the captured lease, scratch owner and completed activity marker. A scope rejection records the successful inspection command's real exit code; the host policy decision is separate. The rejected model outcome and its coordination messages remain audit evidence, never accepted success.

Automatic scratch-content recovery requires the exact `git diff --cached --check` command, integer exit code 2, empty stderr, and at most 64 KiB of complete recognized path/line content diagnostics. Supported records cover conflict markers, trailing whitespace, space-before-tab, blank-at-EOF, tab-in-indent, indent-with-spaces, and their supported combinations. Missing source lines, empty/error/mixed output, other exits, or unsupported diagnostic formats remain unclassified. The same captured bytes are checked when creating and replaying a journal. Operational errors retain their raw stdout/stderr, original result, scratch and marker, and park without automatic retry, validation or message publication.

Before another opening coordination check, the supervisor may consume only a durable typed failure whose current task, clean canonical HEAD, lease, scratch HEAD/index/worktree, ownership nonce, completed process, and captured bytes still match. It retires only that exact marker, persists bounded actionable retry feedback once, and then clears the pending record. Interrupted journaling or cleanup reuses the original artifact bytes and invocation ledger. The feedback retains the useful rejected draft directly as unvalidated data and preserves the original task and reviewer request. Generic read-only guidance preserves the original deliverables and recipients and bounds each message body at 5,500 characters. A guarded legacy recovery may include separately labeled, bounded task-specific retry guidance in its immutable provenance; that guidance cannot expand the original task authority.

A completed-result capture without a classified durable failure grants no automatic recovery. Missing, malformed or changed ownership, a live process, uncertain publication, or an unrelated human/system blocker stays blocked with its original evidence retained. A separately guarded offline maintenance operation may finish an already proven journal and call `Supervisor.recover_postprocessing_failure(role)` while paused; that method never dispatches a provider or fabricates validation. The first postprocessing exception is retained independently so a later ownership guard cannot erase the original diagnostic.

Earlier runtimes must remain paused and must never consume an unhandled `postprocessing_failure` envelope: its embedded original model result is audit data, not accepted success. Use the reviewed newer validator and consumer first, and verify that the typed pending record and owned marker are absent before any older-runtime recovery or rollback.

### Revision-bound supervisor coordination evidence

The supervisor captures the required Windows coordination check before each implementation attempt and after successful canonical validation and coordination publication. Recovery of an already durable implementation is explicitly labeled as a recovered-checkpoint validation attempt; it is never represented as a historical pre-implementation check. Each capture validates the existing exact-HEAD handoff under the role OS lock before and after execution, refuses unresolved local activity markers or cloud sessions, and includes bounded actual output plus hashes of the complete saved artifacts. Opening and closing observations must share the same lease identity. The closing capture is bound to the exact successful validation-receipt bytes. These are observations of canonical exclusive ownership and registered writers, not independent approval or certification of unregistered external processes.

Task-matching canonical issue files share the review packet's unused capacity after all other sections retain their existing bounds. The default aggregate remains 228,000 section-content characters plus fixed headings and separators; truncation markers count toward that budget. Explicit section-limit overrides remain hard limits. If required issue evidence still cannot fit, the packet remains incomplete and review is blocked before model dispatch.

Review packets include task-matching supervisor messages separately so mailbox bounding cannot hide the required acknowledgment. Missing or critically truncated evidence parks the phase as an evidence blocker before another model invocation instead of degrading to a thin prompt or repeatedly reimplementing unchanged work. A closing-check failure preserves the durable implementation result. Existing cloud work is polled without creating another worker; only completed adoption permits a new recovered-checkpoint capture. API review reads source from an isolated snapshot while checking coordination evidence against the canonical leased checkout, and incomplete evidence is rejected before any API reservation or send. Explicit repository-freeze acknowledgments use the coordination-only validation profile, while security reviews retain their product/security gates.

Model-phase admission and pause commitment share the control-plane lock. A phase starts when the supervisor atomically writes its fresh admission record after reading an explicitly active current policy under that lock. The lock is released before invoking the model or running validation. A phase admitted before pause may execute and finish, even if its callback begins after pause commits; pause prevents later admissions and is not cancellation of admitted work. Missing, unreadable, malformed, or paused current policy fails closed. Scheduler dispatch also checks current policy under the same short lock, and queued workers recheck it before beginning their cycle. These short admission and pause transactions may wait up to two seconds for another process's control-plane ownership, then fail closed; default supervisor and role lease acquisition remains immediate.

Only the latest admission per role is retained in `phase-admissions/<role>.json`. It is an audit record, not an execution result, reusable authorization, or busy lock. If the supervisor crashes after admission, a restart must obtain a fresh admission before any new invocation; an old or malformed audit record cannot authorize work or stall recovery. An already durable pending result may still finish its state transition without a new admission or model call. Backend and mobile invocations remain independent, and pause does not wait for either long-running invocation.

### Deployment subscription-only policy

A pinned Windows deployment may set `ASKREX_PROVIDER_POLICY=subscription_only` before starting the supervisor. This process environment policy overrides stale saved provider flags without editing them. It forbids OpenAI API activation, budget reservation, and sends; Fable selection and invocation; and fresh Claude cloud dispatch or context-delivery messages. The active-invoker factory does not load unused API credentials or require unused project confirmation in this mode. Codex-first planning and independent review remain required; stale temporary Claude planning and hourly review-fallback flags are ineffective, and direct hourly-receipt consumption returns no result. Ordinary Codex work and the existing Claude subscription implementation fallback after a Codex usage/authentication limit continue. Existing cloud sessions may still be polled and adopted through the existing ownership, provenance, validation, and independent-review gates, but receive no new cloud instructions; unresolved mismatched ownership is retained and blocks new work.

Only an unset or empty environment value retains the configured provider behavior for other authorized deployments. Any other nonempty value fails closed as invalid. Policy checks exist at routing and direct effect boundaries, so an enabled configuration flag or an already-created worker cannot authorize a prohibited reservation, send, or delegation. Both active and rollback deployment wrappers must set the same policy.

## Human gates and banked resets

Physical device tests, credentials/login, account or billing changes, security-authority changes, and banked Work/Codex reset consumption are human gates. OpenAI API billing/budget/rate-limit state is separate from ChatGPT/Codex reset accounting and never consumes or recommends a banked reset.

The supervisor records three banked resets initially and reserves the final reset by default. A usage limit may create a `blocked_user` reset recommendation, but the tool never clicks ChatGPT Settings, purchases usage, or decrements the count before confirmation.

After James confirms the platform's remaining reset count with `confirm-resets`, only workers blocked specifically by `usage_limit` are released. `confirm-acceptance` releases only revision-bound acceptance blockers. `resume-human --blocker-kind github_auth|auth|human` releases only the explicitly matching blocker after the operator has completed that external action. Every release restores the saved phase; unrelated blockers remain stopped.

## Watchdog

`scripts/dev_orchestrator/windows_watchdog.ps1` checks only deterministic heartbeat/process state. A heartbeat is healthy only when it has the exact contract, a strictly typed positive integer PID, a timezone-bearing timestamp within bounded future skew, and the exact raw Windows process-creation FILETIME matching the currently live PID; malformed, future-dated, or PID-reused heartbeats are stale. It contains no Codex, Claude, or model invocation logic. Windows Task Scheduler may run it every 30 minutes. The watchdog never kills a live supervisor. For Claude markers it checks the uniquely named Docker container as well as the client PID; if the client died but the scratch-only container remains, it force-removes that orphan container before clearing the marker. If Docker state is unavailable or ambiguous it refuses restart. It starts a replacement only when heartbeat/process/container evidence proves no model child may still be running.

The supervisor itself performs frequent deterministic checks. A background heartbeat remains fresh while a long Claude/Codex subprocess is running, so the watchdog must not mistake legitimate model work for a dead supervisor.

During continuous operation each role has at most one active cycle. The loop reloads configuration before each role dispatch, so a long backend validation does not prevent the mobile role from advancing. Pausing suppresses new dispatches; it does not cancel an active operation. The supervisor keeps its single-instance lock and heartbeat until active operations drain, including when the scheduler fails. A role-specific lease or invoker-startup failure blocks that role while healthy peers continue; pending results, existing leases, original resume phases, and existing human or non-resumable system blockers are preserved. Invalid shared configuration or coordination transaction state still stops the controller. Manual `cycle` still waits for both roles.

## Rollout rule

Never let browser-based coding workers and CLI orchestrator workers write the same worktree concurrently. Initialize and test in observe-only mode. For each role use `request-handoff`, have the trusted local operator verify the active browser worker checkpointed/stopped, record `operator-ack-handoff` with the request nonce and browser-session correlation ID, then `accept-handoff` after the quiescence recheck. Activation remains forbidden until both exclusive leases validate. Any external writer invalidates the lease and blocks further mutation.

## Completion gate

Planner/adjudicator `done` claims are advisory only, and Astra may not mark an active task done before independent review. Each repository has an explicit completion manifest. Before a workstream becomes `done`, the deterministic gate requires no non-deferred owned open or `fixed-needs-retest` issues, a clean leased worktree, revision-bound documentation-truth acceptance, recorded physical acceptance, recorded cross-repo contract acknowledgment, a CI workflow, an OPEN pull request at the exact current HEAD and expected base branch, every mandatory named CI check present with conclusion SUCCESS, and every local release-quality command passing. An owner-deferred issue remains open canonical work; it is excluded only from the currently authorized campaign scheduling/completion calculation until explicitly resumed. A final independent **Codex GPT-5.6 Sol** review runs only after those deterministic gates pass and always bypasses the OpenAI API worker, even when paid routing is enabled and budget remains. Missing GitHub authentication is a `blocked_user` credential boundary, not a coding task. `SKIPPED` or `NEUTRAL` never satisfies a required check.

Final verification is a durable reserved `FINAL-VERIFY-<role>` task bound to the clean leased HEAD. Its preparation phase runs the canonical completion manifest through the existing validation runner, even when ordinary iteration validation is disabled or scoped. The successful receipt contains the actual local gate outputs and observed CI/acceptance evidence, and opening/closing supervisor captures bind that receipt. The independent final Codex reviewer receives this complete packet. Pause or restart resumes final verification directly; a persisted review checkpoint or durable reviewer result does not rerun implementation or the successful local gates. An explicit new planner completion claim first preserves prior canonical receipt and manifest bytes in content-addressed history, leaving their capture files intact. The durable planner result remains pending until the new reserved task state commits, so interrupted retirement is replayable and cannot discard a new attempt's validation. A preparation interrupted before its phase save keeps the original opening capture. A valid same-revision final receipt resumes only the missing closing check; a complete checkpoint advances directly to review without rewriting its receipt or captures. Recovery verifies the canonical final gates, current lease and script, captured output hashes, and receipt time between the opening and closing observations. Present malformed, stale or mismatched evidence is preserved and blocks recovery. Missing or changed proof remains blocked. Only a passing independent review plus a fresh same-HEAD CI, acceptance, lease, and evidence recheck permits `done`.

## Rejected structured-result contracts

The `issue_updates` API remains limited to owned, open or fixed-needs-retest `TEST-###` live-test issues whose full identifier occurs in the bound task ID. A reference in a task prompt is insufficient. SECURITY, ROADMAP and other work uses authorized structured coordination messages. The producer prompt and bound Codex schema state this restriction explicitly; the host still checks current ownership and status.

A deterministic result-contract rejection invalidates the entire result before publication. The supervisor saves the original parsed result and real pending envelope under `rejected-results/`, then atomically commits bounded current correction feedback and the consumed invocation ID before clearing the journal. The next attempt stays in the same phase, including final review, and must produce a fresh valid result. The rejected PASS and its messages are never accepted or replayed. The separate contract-failure counter permits at most three rejected attempts before parking without automatic resume; existing implementation/review counters and canonical receipts are preserved. A valid accepted result clears this correction state. Publication or transaction failures keep the pending result for idempotent recovery instead of requesting a new model result.

An older consumed `invalid live-test issue id` review blocker can supply its known host reason to normal review resumption. This is labeled as prior host rejection, not a reconstructed result or review approval. No one-time pending-envelope reconstruction or canonical gate rerun is required. Keep older runtimes paused during rollback so they cannot silently discard the new correction state and repeat rejected requests.

## Worker context and model dependency waits

Implementation receives complete explicitly referenced canonical issue requirements, including accepted-requirements documents, before optional mailbox history. Required sources that are missing or exceed the bounded context capacity stop model dispatch. Reading a requirement does not change its owner, deferral, privacy, approval, or verification rules.

Host status identifies the exact task, repository revision, receipt and matching failure artifacts. A prior-task baseline does not validate the current task or close a broader campaign issue. A newer matching failure remains authoritative over an older receipt; an old-head receipt cannot describe the new revision as passed. A receipt without complete current host captures is reported conservatively. Independent review and canonical validation gates remain unchanged.

Task-relevant outgoing proposals are supplied alongside incoming coordination. An outgoing proposal is not approval or peer agreement. Workers must reuse the existing proposal and obtain the actual required response before implementation, without inferring new permission from the proposal itself.

A valid non-human model blocked_system result is archived under model-blockers/ before its authorized coordination publication. The immutable record preserves the original parsed result, pending envelope, phase, task/base revision and first observation. The input_provenance field binds the pending result to the exact supplied-context digest and stable external-input fingerprint recorded at phase admission. The admission remains an audit record, never reusable permission or a busy marker.

The state fields model_blocker_phase, model_blocker_feedback and model_blocker_fingerprint retain bounded actionable context. The role waits as blocked_system/model_dependency while relevant external inputs are unchanged. Incoming peer replies, requirements, current HEAD or task-bound validation evidence can wake the same phase. Invocation IDs, new timestamps, retained blocker feedback, the role's own capture refresh and outgoing publications cannot wake it. The baseline precedes model execution and lock waits, so a reply arriving during an invocation is not swallowed by a later snapshot.

Archive, transactional publication, atomic state transition and pending-result cleanup preserve replay identity. Host I/O, publication failures, uncertain process outcomes, human gates and transient runner recovery keep their existing paths. Legacy consumed model reasons may receive one truthfully labeled corrected attempt; no old result or passing receipt is reconstructed.

Keep earlier runtimes paused during rollback. They do not understand model dependency wait semantics and must not consume an unhandled new blocker journal or blindly resume this state. Use the reviewed current archive validator and consumer before resuming an older runtime.

### Exact supplied input and queued assignment recovery

The admission fingerprint describes the external input baseline selected before
any provider-slot wait. Its source_context_sha256 identifies that selected
source context, not the final review rendering. The provider adapter preserves
the exact rendered CLI prompt or prepared API request body in
model-inputs/<role>-<sha256(invocation_id)>/input.txt, with its byte length, SHA256,
and original phase-admission record in manifest.json. The pending result and
model-blocker archive bind the supplied_input descriptor. The read_supplied_input
validator reads those immutable artifacts without acquiring diagnostic lease
locks or rebuilding context.

Explicit requirements and task-related incoming and outgoing correspondence are
complete critical inputs. They precede unrelated mailbox history, including in
review. If they do not fit the existing packet budget, dispatch stops visibly.
An outgoing proposal remains a proposal; only an actual peer response can supply
agreement, and all task, ownership, approval, and validation gates still apply.

An eligible unchanged-input wait appends one model_dependency_wait event to
logs/model-dependency-checks.jsonl under a fresh unpaused policy check. The event
binds the blocked invocation and original admission to both equal fingerprints;
it does not grant permission or become a wake input. No event or counter is
invented for a pause, an already-present reply, or a reply arriving during a slot
wait.

Explicit queue selection first writes queue-claims/<role>.json with the exact
before/after state and queue. State assignment commits before queue removal.
Role entry and enqueue finish an interrupted claim under the control-plane lock
before other work. Unknown or conflicting claims remain blocked and intact.
Earlier runtimes must remain paused while a queue claim or new model-blocker
checkpoint is unhandled; use the reviewed newer recovery code first.

### Referenced prior-task replies

An active task that explicitly names an accepted prior task may receive the role's complete earlier replies as historical evidence. Each selected reply must match its host-generated message filename, immutable invocation input, original task identity, and accepted-completion time bound. Preserve the reply's stated scope: a completed-task record alone does not establish broader agreement or permission. Current-task outgoing text cannot become an external wake input by naming an older task or inserting an Invocation header.

## Completion work and host draft publication

A taskless completion claim triggers deterministic preflight. Local CI or release-gate defects become bounded implementation tasks that still require canonical validation and independent review. Missing CI uses a stable role task ID; repeated material failures are bound to source content and stable gate facts. If an accepted obligation remains unsatisfied, preserve its history and require an explicit regression task instead of silently repeating the accepted task.

Host publication is operator-controlled and enabled only when `metadata.host_publication.enabled` is the literal boolean `true`. The host requires a clean leased branch, an accepted independent review and complete canonical validation for the exact HEAD, an allowlisted repository origin, a live supervisor identity, and fresh unpaused policy. It pushes one explicit branch normally and creates new pull requests as drafts using the recorded body file. Existing pull-request readiness is preserved. Publication does not confirm documentation, cross-repository or physical acceptance and does not merge a branch.

Every remote mutation has a durable admission journal. An unknown outcome permits read-only reconciliation, not another blind mutation. A definitive workflow-scope authentication denial requires the documented `resume-human --blocker-kind github_auth` after the operator resolves the external authentication issue. That resume is consumed before retry; another denial cannot reuse it.

Pending CI and retryable observation failures use host-only observation waits. Actual failed or missing required checks become local remediation; additional hard-failing checks retain their distinct observed names and cannot be waived merely to obtain a pass. Eligible explicit queued work may proceed from non-human completion waits while publication journals remain intact for later reconciliation. This does not release authentication, human, live-test or retest holds. Final completion still requires current-revision acceptance and all configured local and GitHub gates.
